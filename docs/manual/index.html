01

What you are building

A quiz application has two halves, and keeping them apart is the whole idea of this system.

HalfWho owns itWhat it is
The systemThese packagesThe rules of the game, the state machine, the scoring, the screens, the sounds, the start menu, the colours
The contentYour applicationThe questions, the pictures, which quizzes exist, how a round is dramatised, which language it is played in

You will never write a state machine, a scoring rule or a scene. You write a quiz package — three JSON files and a directory of media — and hand it to a runtime. Everything you can change without touching code is content, and that is deliberate: a new quiz, a new language or a new picture must never need a new program version.

The four libraries

PackageYou use it forDo you need it?
@hfroemmel/quiz-coreLoading a package, running a game, the typesrequired
@hfroemmel/quiz-reactThe playable quiz as one React componentrequired
@hfroemmel/quiz-themesPalettes, fonts, your own lookrequired
@hfroemmel/quiz-contentThe quiz-content command line tool: validate, build, importrequired (build time)
 All four carry the same version number and are released together. A fifth, @hfroemmel/quiz-kiosk, existed up to 0.19.0 and pointed at quiz-react; it is gone. Whatever it exported, quiz-react exports.

Prerequisites

  • Node.js 20 or newer, and pnpm or npm.
  • A GitHub account with read access to the @hfroemmel packages (step 2).
  • React 18 and TypeScript. The examples are TypeScript; plain JavaScript works too, you just lose the type checking that catches a misspelt configuration key.

The shortest possible summary

Write content/source/{config.json, questions.json, assets.json}. Run quiz-content build. Load the three files it produces with loadQuizPackage, give them to a LocalQuizRuntime, and render <QuizGame runtime={runtime} />. That is a complete quiz application. The other twelve steps are detail.

02

Access to the packages

The libraries are private packages on GitHub Packages, not on the public npm registry. Two things are needed: a line telling your package manager where the @hfroemmel scope lives, and a token proving you may read it.

In the project

.npmrc

@hfroemmel:registry=https://npm.pkg.github.com

This file belongs in the repository. It contains no secret.

On your machine, once

Create a classic personal access token with the read:packages scope (GitHub → Settings → Developer settings → Tokens (classic)) and put it in your personal ~/.npmrc:

~/.npmrc

//npm.pkg.github.com/:_authToken=ghp_your_token_here

Never commit the token

It goes in ~/.npmrc, never in the project's .npmrc. In CI you do not need a token at all: grant the workflow permissions: packages: read and write //npm.pkg.github.com/:_authToken=${{ secrets.GITHUB_TOKEN }} into the runner's .npmrc as a step.

Pin the version

Use a tilde range, not a caret and not 0.x. Below 1.0 a minor version may break the view model, and a caret range would pick it up silently:

"@hfroemmel/quiz-core": "~0.19.0"
03

Create the project

pnpm create vite my-quiz --template react-ts
cd my-quiz
printf '@hfroemmel:registry=https://npm.pkg.github.com\n' > .npmrc
pnpm add @hfroemmel/quiz-core@~0.19.0 \
         @hfroemmel/quiz-react@~0.19.0 \
         @hfroemmel/quiz-themes@~0.19.0
pnpm add -D @hfroemmel/quiz-content@~0.19.0

quiz-content is a development dependency: it is the command line tool that turns your source files into a package. It never runs in the browser.

Add the two content scripts

package.json

{
  "scripts": {
    "content:validate": "quiz-content validate",
    "content:build": "quiz-content build",
    "dev": "pnpm content:build && vite",
    "build": "pnpm content:build && vite build"
  }
}

Wiring the content build in front of dev and build is worth doing on day one. It is the difference between “the quiz is stale because someone forgot a command” and a project that cannot be built with broken content.

Why content/source and not src/content

The quiz-content tool has one convention: it looks for content/source, content/dist and content/reports under the current working directory. You can override each with --source, --out and --report, but following the convention means every command works with no flags.

04

The content directory

Three files, and each one answers a different question.

FileAnswersShape
config.jsonWhich quizzes exist, how a round runs, what things are calledone object
questions.jsonWhat is askedan array of questions
assets.jsonWhich media files exist and who they belong toan array of assets
assets/—the actual files

Everything is referenced by id. A question names a difficulty id, a category id, a pool id and an asset id; the configuration defines what those ids mean. Nothing is matched by label, so renaming a label is always safe and renaming an id never is.

Ids have a format

Lower case only: a-z, 0-9, dot, hyphen and underscore, starting with a letter or digit. Bundestag_Quiz is rejected; bundestag-quiz is fine. The rule exists so that ids cannot fall apart over capitalisation between a spreadsheet and a file name.

Section by section

questionsPerGame

How many questions a round has by default. A preset with a different number of slots wins — the slots are the truth about the length of a round.

difficulties, categories, pools

Three independent vocabularies your questions draw on.

  • Difficulty is exactly one per question.
  • Categories are a list per question — subject matter, used by slot filters.
  • A pool is a body of content, not a mode and not a category. “Bundestag” and “Saarbrücken” are pools. Which pools a game draws from is decided when a game starts.

themes

A theme in the content chooses a design world, not colours. Two worlds exist: skin: "default" (the dark stage) and skin: "kids" (the illustrated, drawn world). Leaving skin out means default. Colours come from step 11 and are the host's business, not the content's.

audiences

Who is playing — adults, children. An audience carries the start screen's title, description and background image, points at a theme, and limits which presets may be used (allowedPresetIds). Every question declares the audiences it suits.

presets — the dramaturgy

This is the part that is unlike other quiz systems, and the part worth understanding. A preset is a list of slots, and each slot is a filter describing what kind of question may stand in that position. The engine then picks a question per slot, avoiding repeats.

FilterRestricts to
difficultyIdsQuestions of these difficulties
questionTypestext-choice, image-choice, person, image-reveal
hasVideotrue demands a question with a video, false excludes one
evaluationModesoption-comparison (machine-checked) or manual-correct-incorrect (a human decides)
categoryIdsQuestions in these categories
tagsQuestions carrying these tags
 A missing filter means “anything”. There is no random keyword, because an empty filter already is one.

The single most common mistake

If your quiz is played without an operator — a kiosk, a touch table, a web page — then every slot must filter "evaluationModes": ["option-comparison"]. A question that has to be marked right or wrong by a person is unplayable when there is no person, and a preset with even one such slot is not offered for self-service play. The engine derives this from the filters; there is no second flag to set.

quizzes — what the start menu offers

FieldMeaning
id, labelIdentity and the name on the card
labelsThe name in other languages: { "en-GB": "Bundestag Quiz" }
audienceIdWhich audience this offer belongs to
themeIdWhich design world it is played in
presetIdsThe difficulties offered for it, in order
defaultPresetIdPre-selected in the menu
playerCounts[1] solo only, [1, 2] also a buzzer duel
emphasiswide gives the card a whole row, regular shares one
orderSort order in the menu. Leave gaps: 10, 20, 30

Three optional top-level sections complete the picture and are covered later: locales and interfaceStrings in step 12, rules in step 13.

Two questions are not a quiz

The preset in step 5 has five slots, so a round needs five questions that satisfy five different filters. The two above satisfy two of them. Validation will tell you exactly that, and the start menu will refuse the quiz with a reason rather than starting a round it cannot finish. Write enough questions per slot that three rounds in a row do not repeat — for a five-slot preset that means roughly four to five candidates per slot, not five questions in total.

The four question types

TypeWhat the player seesNeeds
text-choiceQuestion and answer rowsoptions
image-choiceA picture, then answer rowsoptions + image

image-revealA picture that sharpens over time — buzz early, score moreimage; options optional
 A question with fewer than two options is never treated as a choice, whatever its type says: one row would be the solution itself.

summary versus details

explanation.summary is for whoever runs the game — it appears at the operator's desk and is never projected. explanation.details is for the player: with the rule showDetailsAfterSolution (step 13) it becomes a step of its own after the solution, with its own way onward. In a hall you leave that rule off, because the moderator tells the background out loud.

Every medium is declared once in assets.json and referenced by id from the questions. A question never names a file path.

    "mimeType": "image/jpeg",
    "credit": "Foto: Deutscher Bundestag / Julia Nowak"
  },
  {
    "id": "start-adults",

    "credit": "Eigene Grafik"

FieldNotes
idWhat a question or an audience references
kindimage, video or audio
filenamePath under assets/, subdirectories allowed and encouraged
mimeTypeServed as-is; get it right or a browser will refuse the file
creditThe licence line. Optional in the schema, never optional in practice

Fill in credit from the start

A missing credit is reported as a warning, so a build with unattributed pictures succeeds. That is how an existing corpus in this project ended up with uncredited images. The import names them per question the moment it reads a table, which is where the gap is cheapest to close.

The video-free profile

Video files are large and an offline kiosk usually cannot carry them. Build with --profile no-video and the pipeline drops video assets and every question that needs one:

quiz-content build --profile no-video

The same flag exists on validate, so the check matches what you ship. A preset slot that demands a video ("hasVideo": true) becomes a free slot in that profile — the number of slots stays, only the clip is gone.

Working without the real pictures

Two helpers make an early start possible. --placeholder-media turns a missing file from an error into a warning and lets the build finish; quiz-content demo-assets generates placeholder graphics for every declared asset, so the screens have something to show.

08

Build the package

Check first, build second:

pnpm content:validate
pnpm content:build

Validation reads your three files and reports two kinds of finding. Errors stop the build and write no package at all — a broken schema, an id that points at nothing, a duplicate id, a missing media file. Warnings let the build through: an unused pool, a question no slot can reach, a missing credit, a prompt longer than the board can hold.

The build writes four things into content/dist and a readable report into content/reports/build.md:

FileWhat it is
manifest.jsonVersion, checksum, the asset list — the package's identity card
config.jsonYour configuration, normalised
questions.jsonYour questions, normalised
assets/The media files, copied

The version number rises by itself: the first build is 1.0.0, each later one increments the patch. Set CONTENT_VERSION in the environment to choose your own. The checksum covers configuration, questions and assets together, so a package cannot be half-updated without being noticed.

Do not edit content/dist

It is generated, and the next build overwrites it. Commit it or don't — both are defensible. Committing means a clone can run without a build step; not committing keeps the repository small. Whichever you choose, the report under content/reports is worth reading after every build: it lists the coverage of every slot of every preset, which is how you find out that the “finale” slot has exactly one candidate question.

The slot coverage table in that report is the single most useful output of this system. A slot with too few candidates will repeat the same question every round; a slot with none makes the quiz unstartable, and the start menu will say so instead of failing.

09

Load it in the browser

The built package is three JSON files and a directory of media. A browser application serves them as static files. The simplest route with Vite is to copy content/dist into public/quiz:

package.json

{
  "scripts": {
    "content:build": "quiz-content build && node -e \"require('fs').cpSync('content/dist','public/quiz',{recursive:true})\""
  }
}

Now write the loader. This is the only code in your application that knows where the files are.

src/quizPackage.ts

import { loadQuizPackage, type QuizPackage } from '@hfroemmel/quiz-core'

/** Where the built package is served from - see the content:build script. */
const base = '/quiz'

export async function loadPackage(): Promise<QuizPackage> {
  const read = async (name: string): Promise<unknown> => {
    const response = await fetch(`${base}/${name}`)
    if (!response.ok) {
      throw new Error(`${name} could not be loaded (${response.status}) - run "pnpm content:build" first.`)
    }
    return response.json()
  }

  const [manifest, config, questions] = await Promise.all([
    read('manifest.json'),
    read('config.json'),
    read('questions.json'),
  ])

  // Reading AND checking is the package's job - it parses every schema and
  // throws on the first thing that does not fit.
  return loadQuizPackage({ manifest, config, questions })
}

/**
 * Asset id -> URL.
 *
 * Without this the core builds `/media/<id>`, which is the route a quiz
 * SERVER serves. A static site has no such route, so it says here where its
 * files are: the manifest carries the file name for every id.
 */
export function mediaUrl(quizPackage: QuizPackage) {
  return (assetId: string): string | undefined => {
    const asset = quizPackage.assetsById.get(assetId)
    return asset ? `${base}/assets/${asset.filename}` : undefined
  }
}

If pictures do not appear, this is why

Asset ids are resolved to URLs by the host, not the core. Leave the media option out and every image request goes to /media/<asset-id> — correct behind a quiz server, a 404 on a static site.

10

Render the quiz

Two files and you are playing.

src/main.tsx

import { StrictMode } from 'react'
import { createRoot } from 'react-dom/client'
import { App } from './App'

/*
 * The four global stylesheets, in this order. They are deliberately not CSS
 * modules: the transition registry names its keyframes as strings, so those
 * names must not be hashed.
 *
 *   palette  every colour value, generated from quiz-themes
 *   fonts    the @font-face rules
 *   motion   keyframes and transition classes
 *   stage    the stage's root classes, which every component reaches into
 */
import '@hfroemmel/quiz-themes/palette.css'
import '@hfroemmel/quiz-themes/fonts.css'
import '@hfroemmel/quiz-react/styles/motion.css'
import '@hfroemmel/quiz-react/styles/stage.css'

createRoot(document.getElementById('root')!).render(
  <StrictMode>
    <App />
  </StrictMode>,
)

src/App.tsx

import { useEffect, useState } from 'react'
import { LocalQuizRuntime } from '@hfroemmel/quiz-core'
import { QuizGame } from '@hfroemmel/quiz-react'
import { loadPackage, mediaUrl } from './quizPackage'

export function App() {
  const [runtime, setRuntime] = useState<LocalQuizRuntime | null>(null)
  const [error, setError] = useState<string | null>(null)

  useEffect(() => {
    // Whoever creates the runtime disposes of it. A load that is abandoned
    // half way must not leave a running game behind.
    let discarded = false
    let built: LocalQuizRuntime | null = null

    void loadPackage()
      .then((quizPackage) => {
        if (discarded) return
        built = new LocalQuizRuntime({ quizPackage, media: mediaUrl(quizPackage) })
        setRuntime(built)
      })
      .catch((cause: unknown) => {
        if (!discarded) setError(cause instanceof Error ? cause.message : String(cause))
      })

    return () => {
      discarded = true
      built?.dispose()
      setRuntime(null)
    }
  }, [])

  if (error) return <p>The quiz could not be loaded: {error}</p>
  if (!runtime) return <p>Loading…</p>

  return <QuizGame runtime={runtime} audience="adults" />
}
pnpm dev

You get a start menu — which quiz, how many players, how hard — and a playable round. The menu, the buzzer, the scoreboard, the sounds, the solution and the result screen all come from that one component.

What QuizGame takes

PropEffect
runtimeThe game to play. Leave it out and the component connects as a player to the server that delivered it — that is the stage-night case, not yours
audienceWhich audience this device plays in. Without one, the first in the configuration
playerCountsNarrows what the configuration offers. [1] removes the “how many are playing” question entirely

When the menu refuses to start a quiz

A quiz with no questions, or whose pool is missing, is shown with its reason and a disabled button rather than failing on the attempt. That is the system telling you your content does not cover your configuration — go back to the build report and look at the slot coverage.

11

Theming

Out of the box the quiz looks like the quiz. Three levels of change are available, and they are not interchangeable.

LevelWhat it changesWhere it is stated
World (skin)The layout — the dark stage or the illustrated children's worldContent: themes[].skin
Look (theme)Colours, fonts, word mark, start visualYour code: a ThemeDefinition
Frame (chrome)Which parts of the frame the quiz draws at allYour code: QuizProvider
 A different arrangement is a new world, not a theme. skin chooses a world; it does not configure one.

Your own look

A ThemeDefinition is one object that says everything: which built-in set it starts from, what it overrides, which fonts it brings, which drawings.

The colour tokens

An override names only what differs from the built-in set; everything you leave out stays as it is. These are the eighteen names tokens.colors accepts:

Surfaces  pageTop  pageBottom  stageTop  stageBottom  controls
Tiles     tile  tileDisabled  tileQuiet  option
Meaning   accent  accentQuiet  primary  solution  solutionChip  correct  incorrect
Type      text  textMuted

tokens.stage and tokens.start take raw CSS custom properties instead — --stage-radius, --stage-button-radius, --stage-fade-duration for the stage; the --start-* family for the menu in front of it. Read them off the built-in stylesheets rather than guessing: an unknown property name is not an error, it simply has no effect.

Light, dark, red — and who decides

The adults' stage ships in three colour variants. Hell is paper, dunkel the darkened hall, and rot is that dark set with one thing exchanged: the ground becomes #CD3363 (Rot at 80 percent). Everything else stays — the surfaces are white veils at five to nine percent and become lighter red over it by themselves, and the three signals keep their meaning in every variant (blue for the selection and the player on turn, green for the right answer, red for the wrong one).

Which one is on show is a preference of the window, not game state: it lives in localStorage under quiz.stageTheme, reaches every window of the same origin, and the server never learns about it. useStageTheme() reads and sets it, and stageThemes is the list of variants that exist — build your own switch from that list rather than from three literals.

A host theme overrules it: base says which set yours is designed for, and for that world the window's preference no longer applies. Whoever designs a dark stage has designed it dark. The children's world has no variants at all — it brings its own paper.

Wrap the quiz in a QuizProvider and it applies:

import { QuizProvider, QuizGame } from '@hfroemmel/quiz-react'
import { houseTheme } from './theme'

<QuizProvider theme={houseTheme}>
  <QuizGame runtime={runtime} audience="adults" />
</QuizProvider>

Why a provider and not a stylesheet

The package's palette.css declares its values on :root — the fallback layer for a page showing one quiz. Overriding them on the document works until there are two quizzes on one page, and then whichever declaration came last wins for both. QuizProvider puts the variables on its own element instead, and CSS custom properties only inherit downwards. Two providers side by side cannot recolour each other.

It uses display: contents, so it carries values without adding a box to your layout.

A host theme does not repaint the other world

Your theme states the design of its world, identified by id and skin. If your package also has a children's quiz, that world keeps the drawing that belongs to it — otherwise an adult stage theme would paint the children's paper in its colours. To theme both, provide two definitions, one per world.

When your application draws part of the frame

If your app already has a header with your logo, a way back and a settings button, you do not hide the quiz's with CSS. You say what you supply, and those parts are not rendered at all:

<QuizProvider theme={houseTheme} chrome={{ brand: false, abort: false }}>
  <QuizGame runtime={runtime} audience="adults" onExit={backToMenu} />
</QuizProvider>

brand is the word mark in the header, abort the chip that ends a running round, settings the gear. Anything you do not name stays as it is.

Ending a round is not the way out of your application

abort is the quiz's own control: a compact chip at the top centre of a running round — Runde beenden, with a cross — which asks for confirmation and then ends the round, resets the state and hands back the quiz's start menu. It appears only while a round runs: not in the start menu, not in the result view, and never on a stage, which is a different component altogether.

onExit is the other thing: it leaves the quiz and returns to your application. If your own frame carries a way home, keep it — but do not switch abort off for it. They are two different promises, and a round left standing behind a way home is a round the next visitor walks into mid-question.

The chip looks the same in every variant, light grey with dark blue on it, because whoever wants out of a round should not have to look for a different button on a dark stage than on paper.

What theming deliberately cannot touch

  • The geometry of the scenes. A different arrangement is a new world.
  • Timings that carry game meaning — the reveal grid, the feedback durations. They are fairness, not taste. (Adjustable as rules, in step 13, where they belong.)
  • The operator's chrome (--ui-*). It is a tool seen for hours at a desk, and it is not part of what a room sees.

For buttons and form fields your application draws outside the stage, and which should match it, import @hfroemmel/quiz-themes/controls.css.

Texts and languages

There are two kinds of visible text, and they live in different places.

KindExamplesComes from
The words of the program“Punkte”, “Richtig!”, “Los geht's”, “Spiel beenden”@hfroemmel/quiz-react — 52 keys, German and English
The words of the contentQuestions, answers, category and quiz names, the start screen's titleYour config.json and questions.json

This split is why a quiz runs correctly with no language configuration at all: the package speaks German and English by itself. You only state what you word differently.

Offering a second language

content/source/config.json

{
  "locales": [
    { "id": "de-DE", "label": "Deutsch" },
    { "id": "en-GB", "label": "English" }
  ]
}

The label is written in that language — “Deutsch”, not “German” — because it is read by somebody looking for their own. The first entry is the base language. With one entry or none there is nothing to choose and no switch appears.

Translating the content

Every label in the configuration has a plural sibling that takes a locale map:

{ "id": "bundestag", "label": "Bundestagsquiz", "labels": { "en-GB": "Bundestag Quiz" } }

The same pattern applies to subtitles, startTitles and startDescriptions. Questions carry a translations map:

{
  "id": "bt-seats",
  "prompt": "Wie viele Abgeordnete hat der Bundestag mindestens?",
  "options": [{ "id": "o1", "text": "598" }, { "id": "o2", "text": "400" }],
  "correctOptionId": "o1",
  "translations": {
    "en-GB": {
      "prompt": "What is the minimum number of members of the Bundestag?",
      "options": [{ "id": "o1", "text": "598" }, { "id": "o2", "text": "400" }]
    }
  }
}

Option ids must not move

A translated option keeps the id of the original. Scoring compares against correctOptionId, so a translation that renumbers its options changes which answer is right. Translate the text, never the id.

Rewording the program's own words

If “Allein” should read “Einzelspieler”, you do not fork the package. State the deviation in interfaceStrings, keyed by locale and then by text key:

{
  "interfaceStrings": {
    "de-DE": {
      "kiosk.solo": "Einzelspieler",
      "kiosk.duo": "Duell",
      "kiosk.setupTitle": "Willkommen zum Quiz."
    }
  }
}

State deviations, not translations

The package already ships all 52 keys in German and English. An interfaceStrings block that restates every English key is a translation nobody reviews, and it will drift from the package's own wording with the next release. List only what your installation genuinely words differently. A third language is the exception: there, every key has to be stated, and no new program version is needed for it.

The key names are stable and grouped by where they appear: stage.* on the stage, feedback.* for right and wrong, result.* on the result screen, kiosk.* at the device, start.rejected.* for an offer that cannot start. Placeholders in braces are filled by the quiz: {player}, {current}, {total}, {count}, {correct}, {joker}. Keep them.

Rules of the house

Scoring, timings, jokers and the idle watch are configuration, not code. Every value has the system's own constant as its default, so a package with no rules block plays exactly as the quiz always has.

content/source/config.json

{
  "rules": {
    "scoring": {
      "firstAnswerPoints": 100,
      "secondChancePoints": 50,
      "manualAdjustmentStep": 10,
      "minimumScore": 0
    },
    "timing": {
      "correctFeedbackMs": 2500,
      "incorrectFeedbackMs": 2500,
      "solutionDelayMs": 500,
      "imageRevealDurationMs": 20000,
      "pauseScreenMs": 3000,
      "questionLeadInMs": 4000,
      "videoLeadInMs": 1000
    },
    "jokers": { "enabled": false },
    "idleTimeoutMs": 120000,
    "showDetailsAfterSolution": true
  }
}

Choosing an idle timeout

An unattended kiosk wants one — two minutes is a reasonable start — so a half-played round does not block the machine for the next visitor. An attended installation with somebody explaining the quiz wants 0, because the watch would interrupt the explanation.

14

Embedding, and the stage variant

QuizGame is the whole quiz including its start menu. Two other shapes exist.

Inside an existing application

A menu, a launcher, a collection of games: keep your own frame, hand over a way back, and say which parts of the frame you supply yourself.

function QuizCard({ onBack }: { onBack: () => void }) {
  const runtime = useQuizRuntime()   // your own hook around LocalQuizRuntime

  if (!runtime) return null
  return (
    <QuizProvider theme={houseTheme} chrome={{ brand: false }}>
      <QuizGame
        runtime={runtime}
        audience="adults"
        onExit={onBack}
        onFinished={(result) => save(result)}
        idleTimeoutMs={0}
      />
    </QuizProvider>
  )
}

Because the theme sits on the provider's element and not on the document, two such cards can appear on one page with two different looks.

The stage on its own

QuizScene is the screen without the device's menu and footer — the projection in a hall, or a preview. It takes the runtime and gives you the stage: scene selection, transitions, sounds, scoreboard.

import { QuizScene } from '@hfroemmel/quiz-react'

<QuizScene
  runtime={runtime}
  variant="stage"            /* 'stage' | 'preview' | 'touch' */
  audible={documentVisible}  /* a quiz in a background tab goes quiet */
  onEvent={(event) => console.log(event)}
  pads={{ bottom: <MyFooter />, overlay: <MyBanner /> }}
  headerSlots={{ /* your own header content */ }}
/>

onEvent is how your application learns what happened — a game started, an answer was right, a round finished — without polling the runtime. The events are derived from the snapshot sequence, so nothing is missed and nothing arrives twice.

With a server

Everything above is LocalQuizRuntime: one window, no network, no server. Swap it for RemoteQuizRuntime and the same components play against a quiz server over a WebSocket, with several screens in one game — an operator's desk, the projection, the players' buzzers. Nothing in your content or your theme changes; only the runtime does. That is a different manual, and the reference implementation is the quiz-live repository.

Checklist before you ship

  1. quiz-content validate reports zero errors, and you have read every warning and decided about it.
  2. Every asset has a credit. All of them, not most.
  3. The slot coverage in the build report shows enough candidates per slot that a visitor playing three rounds does not meet the same question twice.
  4. If the installation is unattended: idleTimeoutMs is set, and every slot of every offered preset filters option-comparison.
  5. If a second language is offered: every quiz, preset, audience and category has its labels, and every question its translations. A half-translated round is worse than a monolingual one.
  6. The package version is pinned with a tilde range, and the lockfile is committed.
  7. content:build runs in CI before build, so broken content cannot ship.
  8. The quiz has been played through once on the real screen, in the real size, with sound on.
